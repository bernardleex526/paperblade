## 0. 角色与边界

- **你（GPT）的身份**：独立审查者和验收者，与主执行 Agent（Opus 5.5）相互独立。
- **你只能写**：`docs/review/` 目录下的报告文件。
- **你不能做**：
    - 修改代码、资产、配置、`PRE_PLAN.md` 或 `PLAN_PROGRESS.md`
    - 提交、推送或切换分支（只读的 `git log`、`git diff`、`git show` 可以用）
    - 运行会连接外部服务、产生费用或修改文件的命令。测试会在 Unity 的临时目录里生成缓存，这是允许的
    - 替 Opus 修 bug。发现的问题写进报告，由 Opus 修复，修完后你再复审
- **审查依据**：只认仓库里的文件和你亲自运行命令得到的输出，不认聊天里的口头说法。

## 3. 通用审查维度（每次都要看）

1. **是否符合决策**：实现有没有违背 `PRE_PLAN.md` 第 2 节的决策和第 6.5 节的接口契约？有没有偷偷做了被否决的方案？
2. **测试是否真实**：测试有没有真正断言行为（而不是只断言"没有报错"）？有没有被跳过、被注释掉，或者阈值被放宽？
3. **帧率无关**：计时有没有和帧率绑在一起？打击停顿和慢动作期间，输入缓冲、无敌帧和冷却用的是不是不受时间缩放影响的时钟？
4. **数据驱动**：手感和平衡用到的数值，有没有写死在代码里而不是放进 ScriptableObject？
5. **性能隐患**：每帧有没有产生内存分配，或者调用 `Find`、`GetComponent`？特效和投射物有没有用对象池？
6. **健壮性**：空引用、越界、事件没有注销、时间缩放没有恢复、协程中断后状态残留。
7. **可维护性**：模块边界是否清晰，是否和第 6.3 节的模块划分一致。

## 4. 各节点专项清单

**R1 战斗核心**：

- [ ]  土狼时间、跳跃缓冲、攻击缓冲的时长与第 6.4 节一致，并且在 30、60、144 帧下测试结果相同
- [ ]  二段跳会在落地或贴墙后正确重置；蹬墙跳不能在同一面墙上无限攀爬（除非设计允许）
- [ ]  翻滚的无敌时间覆盖完整，冷却生效
- [ ]  只有判定帧期间能命中；同一次攻击不会重复命中同一目标
- [ ]  韧性归零后进入 1.5 秒破绽；只有破绽状态下才能斩杀；斩杀期间不会被其他伤害打断而出现异常状态
- [ ]  衔接技只在取消窗口内触发，并且会正确触发 `OnSwitchLink`
- [ ]  打击停顿和慢动作结束后，时间缩放一定能恢复到 1（包括暂停、场景切换、主角死亡这几种情况）
- [ ]  键鼠玩家不会触发手柄震动；关闭震动和调整震屏强度的设置生效
- [ ]  敌人前摇不短于设计值，敌人状态机没有死循环或卡死的状态

**R2 配件与进化**：

- [ ]  槽位规则：同类槽才能替换，被替换的配件分解成金币，一个槽不能装两个配件
- [ ]  钩子调用顺序是确定的，有文档说明
- [ ]  **防递归**：配件效果造成的伤害带有来源标记，不会再次触发同一个配件；多个配件互相触发时有深度上限
- [ ]  叠加规则明确（同名配件能否叠加，叠加上限是多少）
- [ ]  配方识别：只有配方组合会触发进化；替换掉配方里的配件后，状态处理正确
- [ ]  进化后，武器层外观、进化招式和图鉴记录三者一致
- [ ]  每个配件都有图鉴文本，掉落池配置和 `parts.md` 一致
- [ ]  配件和进化相关的存档字段与契约一致，有版本号

**R3 关卡拼接器**：

- [ ]  同一个种子一定生成同一张地图（确定性），随机数源不受其他系统影响
- [ ]  门的方向和偏移匹配正确，房间不会重叠，未使用的门都被封住
- [ ]  可通行检查用的跳跃参数直接读取 MovementConfig，而不是另外写死一份；二段跳和蹬墙跳都考虑在内
- [ ]  抽查可通行检查是否误判：人工构造 2–3 个"跳不过去"的模板，检查器应该判定为失败
- [ ]  1000 个种子的测试真的跑了 1000 次，而不是提前退出或跳过；单次耗时达标
- [ ]  主路线长度和支线数量符合决策 #12；配件掉落点的位置合理

## 5. 严重度分级与报告模板

| 等级 | 定义 | Opus 的处理要求 |
| --- | --- | --- |
| 阻断 | 违背已确认的决策，导致崩溃或卡关，测试造假，存档损坏 | 必须修复，修完后复审 |
| 严重 | 明显的 bug，或与帧率相关、可以稳定复现的问题，会影响验收标准 | 必须修复，修完后复审 |
| 一般 | 代码异味、边界情况、可维护性问题 | 记入已知问题，C6 之前处理 |
| 建议 | 改进思路 | 可选 |

**报告模板**：

```markdown
# 审查报告 <编号>

- 审查对象：<提交 SHA> 于 <分支>
- 读取的交接单：docs/handoff/<编号>.md
- 运行的命令与结果摘要：
  - `<命令>` → <通过/失败，关键输出>

## 结论
通过 / 有条件通过（存在一般问题）/ 不通过（存在阻断或严重问题）

## 问题清单
| # | 等级 | 位置（文件:行） | 问题 | 依据（决策编号或契约） | 建议修复方向 |

## 与 Opus 自评不一致的地方
（Opus 在交接单里声称通过、但你复现失败的项目）

## 复审（Opus 修复后追加）
| # | 状态（已修复/未修复/部分修复） | 证据 |
```

## 6. 检查点抽查（S-Cx）

1. 在 `PLAN_PROGRESS.md` 里找出本检查点之前所有标记为"已完成"的任务。
2. 随机抽取至少 3 个任务，重新运行它们的验收命令；属于 C3 或 C6 的，还要检查交接单里的截图和录屏文件确实存在。
3. 逐项写明：Opus 怎么说的，你复现的结果是什么，两者是否一致。

## 7. 最终验收（V）

1. 在 `main` 或者 C6 指定的提交上，运行 `PLAN_PROGRESS.md` 里记录的完整测试命令，包括 EditMode、PlayMode、`LevelGenSeedTests`（1000 个种子）和 `SmokeRunTests`（10 局）。
2. 检查打包日志，确认 Release 包里没有调试功能和作弊键（搜索代码里的编译条件和调试指令入口）。
3. 核对 `docs/handoff/perf.md` 里的 Profiler 证据是否达到第 12 节的指标。
4. 核对 `docs/handoff/C6-final.md` 的内容清单：每一项在代码或数据里都确实存在，数量也和决策一致。
5. 核对 `docs/licenses/` 里音频和字体的授权记录是否完整。
6. 确认 R1–R3 中所有"阻断"和"严重"问题都已复审通过。
7. 与基线对比：已有测试没有变成失败。
8. 输出 `docs/review/V-final.md`：逐项对照第 12 节，标注 ✅、❌ 或"需人工"，并附上命令输出作为证据。
9. **需要人工判断的项单独列成清单交给用户**，不要替用户下结论。这些项包括：手感、打击反馈的观感、在干净电脑上运行、[itch.io](http://itch.io) 页面、试玩时长和重玩意愿、文案。
